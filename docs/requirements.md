# 需求文档：一键整理仓库

> Parent: [index.md](index.md)

本文记录用户提出的原始需求，并将其拆解为可讨论的条目。
本文只记录需求，不做设计决策，不安排实施。

## 1. 原始需求（用户原话）

> 我们准备写一个 SPT (single-player Tarkov) 的 mod。
> 作用是一键整理我们的仓库。
>
> - 仓库逻辑上来说是一个大容器（非官方容器）。
>   里面有背包之类的小容器（官方容器），容器之间可能存在多级嵌套。
> - 核心功能是解析容器上打的 tag，按规则来收纳物品
> - 过程中，我们需要先自动折叠可折叠物品，比如带枪托的步枪、披挂、背包、耳机等
>   一个物品先折叠再放入容器，和先放入容器再折叠，副作用是不同的。
> - 过程中，最好也完成排序。因为每个物品有 AxB 的体积，还可以转置。
>   不同的排序方式会影响空间利用率，导致有些空位无法塞入东西而浪费。
>   可以考虑用 CP-SAT 来求解。
>   一个物品排序后再收纳，和收纳后再排序，副作用也是不同的。

后续补充：

> 新版游戏内部已经提供了 move lock 和 sort lock，要兼容。
> 参考项目 InventoryOrganizingFeatures 里的 `@ml` 和 `@sl` 已经不再需要。

> 1. 标签有限地参考 `@o` 语法。
>    - `<category>` 类别；`n:<name>` 字串匹配
>    - `!` 排除；`||` 或；`&&` 与
>    - 避免使用游戏中的 `&` 和与他对齐的 `|`
>    - `#<number>` 排序 / 优先级，不需要 `:`
>    - `;` 要求显式的闭合
> 2. 修改 tag 后友好的报错提示。
> 3. 扩展 tag 长度上限。

> - 既然括号在名字里，那么也跟 & | 一样从语法中排除。
> - 一个 tag 可以有多条 `@o[#<order>] <expr>;` 规则。
>   比如 `@o#1 n:5.45; @o#3 ammo;`

> 触发方式：直接替代原生的“排序”按键。

> 1. 有必要的话，我们可以把合并堆叠也纳入我们的补丁。
>    毕竟这也是一键整理的业务范畴之内。
>    你可以加入需求文档内。
>    但如果会因此导致跟 UIFixes 冲突的话就算了。
> 2. UIFixes 的 Sort 要尽可能避免，尤其是触发原生的排序，制造了性能损耗。

> 排序结果要尽可能得稳定，而不是点一次变一次。
> 今天的日志里就很能说明问题，老版本经常要 2-4 次排序后，才能收敛。新版本我还没测过。

## 2. 需求拆解

### 2.1 目标

- 为 SPT 4.1.x 编写一个 mod。
- 提供「一键整理仓库」能力。

### 2.2 领域模型

容器层级：

```text
仓库（逻辑上的大容器，非官方容器）
└── 官方容器（背包、箱子等）
    └── 官方容器（可多级嵌套）
        └── 物品
```

- 仓库本身被视为一个容器，但它不是游戏定义的官方容器。
- 背包等官方容器可以放在仓库里，也可以互相嵌套，层级数不固定。
- 容器上可以打 tag。tag 是用户表达收纳规则的载体。
- 每个物品占据 A×B 的格子，并且可以转置（旋转 90°）。
- 物品是否可折叠由游戏自身判定，mod 不维护可折叠物品清单。

### 2.3 核心功能

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| F1 | 按 tag 规则收纳 | 核心 | 解析容器 tag，把物品收进匹配的容器 |
| F2 | 自动折叠 | 必需 | 收纳过程中先折叠可折叠物品 |
| F3 | 排序 / 装箱 | 最好有 | 在容器内排布物品，减少空间浪费 |
| F4 | 兼容游戏内置锁 | 必需 | 遵守游戏自带的 move lock 与 sort lock |
| F5 | tag 报错提示 | 必需 | 修改 tag 后给出友好的报错提示 |
| F6 | 扩展 tag 长度上限 | 必需 | 放宽游戏对 tag 长度的限制 |
| F7 | 触发方式 | 必需 | 直接替代原生的「排序」按键 |
| F8 | 合并堆叠 | 有条件纳入 | 属于一键整理范围，以避免 UIFixes 冲突为前提 |

#### F1 按 tag 规则收纳

- 输入：容器上的 tag 文本。
- 处理：解析 tag 得到收纳规则。
- 输出：物品被移动到规则匹配的容器中。
- 没有匹配容器的物品留在原地。

tag 语法有限地参考 IOF 的 `@o`，采用以下元素：

| 元素 | 写法 | 含义 |
| --- | --- | --- |
| 类别 | `<category>` | 物品类别 |
| 名称 | `n:<name>` | 物品名称字串匹配 |
| 排除 | `!` | 取反，写在原子前：`!ammo`、`!n:foo` |
| 或 | `\|\|` | 逻辑或 |
| 与 | `&&` | 逻辑与 |
| 优先级 | `#<order>` | 紧跟 `@o`，不带 `:`，数字小的先执行 |
| 闭合 | `;` | 带表达式的规则必须显式闭合；裸 `@o` 不需要 |

规则形态为 `@o[#<order>] <expr>;`，一个 tag 可以写多条规则。
示例：`@o#1 n:5.45; @o#3 ammo;`。

- 兜底（宝宝巴士）写裸 `@o`，不带 `;`，接收容器自身过滤允许的全部物品。
  `@o;` 也合法，含义相同。
- `@o ...;` 之外的自由文本允许，用作容器的可读名字。
- 优先级属于规则而非容器：全局所有规则按 `#` 排序，逐条执行。
- 未写 `#` 的规则优先级最低。

不进入语法的字符，原因是它们出现在游戏的类别名或物品名里：

| 字符 | 出现情况 | 处理 |
| --- | --- | --- |
| `&` | 类别名 Weapon parts & mods，物品名 B&T | 只用 `&&` |
| `\|` | 与 `&` 对称 | 只用 `\|\|` |
| `(` `)` | 英文物品名 915 个含括号，如 (Ranger Green) | 不提供括号表达式 |

#### F5 tag 报错提示

- 修改 tag 后，解析失败或规则有歧义时给出友好的报错提示。

#### F6 扩展 tag 长度上限

- 游戏对 tag 长度有限制，写不下完整规则，需要放宽。

#### F7 触发方式

- 直接替代原生的「排序」按键，不新增按钮或快捷键。
- 与 UIFixes 共存时，一次点击不应启动两套整理流程、互相覆盖布局。
- 尽可能避免执行 UIFixes 的 Sort，尤其避免额外触发原生排序造成性能损耗。

#### F8 合并堆叠

- 合并堆叠属于一键整理的业务范围，有必要时可纳入本 mod。
- 纳入的前提是能够避免与 UIFixes 冲突；若无法满足该条件，则不纳入。
- 已确认由本 mod 提供合并功能，不依赖 UIFixes 的安装或合并设置。
  共存时由本 mod 统一执行整理，停用 UIFixes 的冲突入口，保留其其他功能与配置。
- Pinned 堆叠保留位置和堆叠本身，只允许作为接收方补充数量，不作为合并来源。
  Locked 物品不参与合并，Locked 容器连同其内部一律跳过。
- 合并范围沿用整理范围：根容器与带有效规则的容器，未打规则的容器内部不动。
  先统一进行容器内及跨容器堆叠；按 tag 收纳时继续按需补充目标堆叠。
  具体行为见 [feats/stacking.md](feats/stacking.md)。
- 是否为可合并的同类物品、堆叠上限与操作限制由游戏判定。

#### F2 自动折叠

- 整理范围内的可折叠物品先自动折叠。举例：带枪托的步枪、披挂、背包、耳机。
- 可折叠范围由游戏的统一判定入口决定，本 mod 不枚举物品类型。
  原版只有带可折叠或可伸缩枪托的武器和枪托本体可折；
  其他 mod 给披挂、背包、耳机等加上折叠能力时，本 mod 必须自然兼容。
- 折叠发生在放入容器之前。
- 原话明确指出：先折叠再放入，与先放入再折叠，副作用不同。
  因此折叠必须先于放入，顺序不可颠倒。

#### F3 排序 / 装箱

- 目标：提高空间利用率。物品有 A×B 体积且可转置，排布不好会留下无法利用的碎片空位。
- 求解方式：用户提出可以考虑 CP-SAT，作为候选方案。
- 已确认向上压紧、减少占用行数；同一规则的候选无法全部装入时，先最大化放入面积。
- 面积与占用行数相同时，按类别聚合，先最小化父层类别实际占用行 `max-min` 之和，
  再依次优化子层；在类型内部类别链末端追加 TemplateId 虚拟类别，沿用同一层级计分公式。
  采用逻辑分组，所有可移动物品全局参与；固定物品只作障碍，不计入类别跨度。
  高度与类别目标相同时，再依次最小化可移动物品占用格子的行坐标和、列坐标和，尽量向上、向左排列。
  不强制单件物品移动方向，不牺牲前面的空间与聚合目标去填空洞；全部目标相同时保留已有布局与身份。
  最终排布先在每个网格内部依次加权，权重只取自本网格，
  再累加各网格完整分数；不跨网格按类别深度汇总。
- 已确认收纳也参与空间求解：必要时重排目标容器，未选中的候选继续后续规则。
  目标容器原有物品保留，规则之间的优先级不变。
- 收纳的单网格排布或多网格联合选择单次最多 1 秒，整次整理累计 3 秒。
  收纳最多使用 2 秒，剩余额度用于最终排布；已稳定到最优时提前结束。
- 最终排布一次联合求解全部仍可改善的待整理网格，共享剩余预算；
  不按容器大小逐格独立完成排布，不设置仓库最后处理的优先级。
  不为每个容器追加时限，物品仍留在收纳确定的网格内，结果保持原网格对应关系。
  收纳阶段的多网格联合选择不变。
- 排序结果应尽可能稳定、一次收敛，不应把连续点击 2–4 次作为获得稳定布局的正常使用方式。
  物品、数量、尺寸、锁状态、容器规则及排序配置没有外部变化时，重复整理应尽量保持
  每个物品所在容器、网格、坐标与朝向；不能只看占用行数相同就认定稳定。
  没有实际空间、顺序或聚合收益时，不应在等价布局之间反复换位，也不应交换等价物品的身份。
  稳定性不以牺牲已确认的空间利用率、排序和类别聚合目标为代价；若后续点击仍有实际改善，
  应记录首次结果与后续结果的差异，作为首次收敛不足，而不是据此认定稳定性已满足。
  验收须把上次实际落地结果作为下次输入，连续比较逐物品布局、质量与达到稳定所需次数；
  区分同一会话重复点击与缓存失效或重启后重排，不以缓存命中或同一起点重复求解代替验收。
- 具体行为与边界见 [feats/packing.md](feats/packing.md)。

#### F4 兼容游戏内置锁

- 新版游戏内部已提供 move lock 和 sort lock，整理过程必须与之兼容。
- sort lock（Pinned）物品收纳时跳过，不移动。
  游戏在物品移出所在容器时会自动解除 Pinned，跳过是为了不触发这个副作用。
- move lock（Locked）物品及含 Locked 物品的容器，游戏本身拒绝移动，本 mod 同样不碰。
- 参考项目 IOF 的 `@ml`、`@sl` tag 是旧版对这两个锁的替代，已不再需要，
  本 mod 不实现。

### 2.4 操作顺序约束

原始需求两次强调「顺序不同则副作用不同」。这是本需求的关键约束：

| 操作对 | 已确定顺序 |
| --- | --- |
| 折叠 vs 放入 | 先折叠，再放入容器 |
| 排序 vs 收纳 | 收纳时按需重排腾位，收纳完成后统一排布 |

## 3. 边界

以下内容原始需求未提及，不视为需求：

- 整理角色身上的装备（背包、胸挂、口袋等）。
- 战局内（raid）可用。
- 预览、撤销、分步执行。

## 6. 后续优化需求

本节记录 MVP 验收后的新增要求。
实现进度与验收安排见 [收纳优化计划](plans/collection-optimization.md)。

- 多网格容器联合选择收纳物品，考虑各网格尺寸与游戏过滤，
  提高整个容器的装入面积，避免逐网格选择过早占用候选。
- 改善整次 3 秒求解预算的分配，为最终仓库排布保留求解机会。
  采用带结转的 2+1 分配，具体预算边界见 F3 与排布契约。
- 减少收纳阶段重复读取物品、解析规则、扫描与匹配的工作，
  面向更多标签和规则的情况优化，同时保持事务后数据准确。
- 从逻辑上统一查看物品，提前考虑折叠、堆叠和跨容器补充，
  再规划收纳与排布；逻辑展平不代表实际把物品移出容器。
  规划仍需保留所属容器、规则、锁及游戏同类判定。

跨容器堆叠范围已确认：允许带有效规则容器内的堆叠作为来源，
与根容器及其他带有效规则容器之间重新分配数量，仍遵守既有锁与游戏操作限制。
先折叠、再堆叠，然后进入收纳与排布；堆叠不限于收纳阶段向目的地补充。

空间利用率优先，堆叠是减少占格的手段，不以合并次数为目标。
“保留各箱库存”指物品尽可能留在原容器，不要求每箱保留原有数量或至少一堆。
例如两个箱子各有 30/60 发时，允许合成一堆 60/60，释放另一堆占用的格子。
空间收益相同时，优先保留原容器归属、减少不必要的跨容器转移。
